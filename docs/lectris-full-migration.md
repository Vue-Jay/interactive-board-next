# Перенос OnlineRepetitor / Tuqo → Lectris без потери аккаунтов
Актуальный план для Windows и репозитория `Vue-Jay/interactive-board-next`.

> **СТАТУС: подготовка.** Ни одна реальная база данных не скопирована и не переключена.
> Старый проект остаётся основным до успешного контрольного входа и проверки данных.
> Не публикуйте SQL-дампы, пароли, connection string, refresh token и секретные ключи в GitHub или чате.

## Что переносим

1. **Auth:** `auth.users`, `auth.identities`, хеши паролей, UUID пользователей и связанные записи. При корректном полном переносе Supabase Auth пользователям не нужно регистрироваться заново. Сессии на новом проекте обычно потребуют нового входа.
2. **Данные приложения:** `public`-схема, пользователи и роли, права на доски, участники, документы, история, уроки, задания, расписания, шаблоны, чаты, обсуждения, другие таблицы и RPC, реально присутствующие в старой базе.
3. **Файлы:** реальные байты изображений и PDF в Supabase Storage либо в Beget S3 / другом хранилище. Перенос записей `storage.objects` сам по себе **не переносит файлы**.
4. **Настройки платформы:** Auth URL и Redirect URLs, email SMTP, OAuth-провайдеры, Edge Functions и secrets, Realtime publications, Storage policies и buckets, расширения и параметры PostgreSQL.

**Нельзя считать перенос завершённым, пока не проверены все четыре пункта.**

## Этап 0. Ограничения и выбор способа

Официальная документация:

- [Restore to a new project](https://supabase.com/docs/guides/platform/clone-project).
- [Backup and restore using CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).
- [Migrating Auth users](https://supabase.com/docs/guides/troubleshooting/migrating-auth-users-between-projects).

Есть два варианта:

- **A. Автоматический:** в исходном Supabase → Database → Backups → Restore to a New Project. Доступен на **платных тарифах с включёнными physical backups**. Supabase создаёт отдельный проект с копией базы, включая Auth и хеши паролей. Возможна отдельная плата. Storage-файлы, настройки Realtime, Auth и Edge Functions всё равно проверяем отдельно.
- **B. Логический:** создать второй пустой Supabase и использовать `supabase db dump` / `psql`. Подходит, когда автоматическое клонирование недоступно. Требуются Supabase CLI, Docker Desktop и PostgreSQL/psql, свободное место для резервной копии.

**Не запускайте `supabase/setup.sql` и отдельные миграции в новой БД ПЕРЕД восстановлением полной копии старой.** Они уже входят в экспорт старой схемы. Раннее применение может вызвать конфликты и дублирование.

## Этап 1. Подготовка

- Записать старый project ref и новый project ref (это **не пароли**).
- В Supabase Dashboard создать отдельный проект, если выбран путь B. Для пути A использовать Restore to a New Project, вручную пустой второй проект не нужен.
- Не изменять прежние `.env`, Vercel и старый репозиторий `interactive-board`.
- Проверить вместимость и тариф нового проекта, выбрать регион и сделать резервную копию.
- Перед копированием выполнить `supabase/lectris_migration_audit.sql` в **старом** SQL Editor и сохранить только числовые результаты/сводку в безопасном месте.
- **При окончательном переносе зафиксировать момент снимка и на короткое время прекратить изменения в старой базе**, иначе данные, появившиеся после экспорта, не попадут в новую.

Проверка окружения в PowerShell из `C:\Users\user\InteractiveBoardNext`:

```powershell
.\scripts\lectris-migration-preflight.ps1 -OldProjectRef OLD_PROJECT_REF -NewProjectRef NEW_PROJECT_REF
```

Это только локальная проверка: никаких сетевых запросов и изменений БД. Если команды `supabase`/`psql` не найдены, установите инструменты до экспорта.

## Этап 2A. Автоматическое клонирование (если доступно)

1. В **старом** Supabase открыть Database → Backups → Restore to a New Project.
2. Выбрать контрольную точку, прочитать стоимость и запустить создание копии.
3. Сохранить новый project ref и отдельно сгенерированный publishable/anon key.
4. Перейти к этапу 3. Старую базу не изменять.

## Этап 2B. Ручной экспорт и восстановление

Использовать **ровно официальный CLI-путь**. Из исходного проекта взять **Database connection string** (предпочтительно Session pooler, port 5432) через кнопку Connect и пароль базы. Для нового проекта взять отдельную строку подключения и пароль. Не путать со строкой `VITE_SUPABASE_URL` для браузера.

Пример **только для подготовленного локального компьютера**, значения вводятся владельцем в локальной консоли, не в GitHub и не в переписке:

```powershell
# Важно: это соединение с ИСХОДНОЙ базой. В строке содержится пароль.
$env:LECTRIS_OLD_DB_URL = "postgresql://postgres.OLD_REF:PASSWORD@POOLER_HOST:5432/postgres"
# А это соединение с НОВОЙ отдельной базой.
$env:LECTRIS_NEW_DB_URL = "postgresql://postgres.NEW_REF:PASSWORD@POOLER_HOST:5432/postgres"

# Убедитесь, что подключение действительно к разным проектам!
supabase db dump --db-url "$env:LECTRIS_OLD_DB_URL" -f "roles.sql" --role-only
supabase db dump --db-url "$env:LECTRIS_OLD_DB_URL" -f "schema.sql"
supabase db dump --db-url "$env:LECTRIS_OLD_DB_URL" -f "data.sql" --use-copy --data-only -x "storage.buckets_vectors" -x "storage.vector_indexes"
```

Сохраняйте SQL-дампы **только в локальном каталоге** `migration-backups/` (добавлен в `.gitignore`). Не выполняйте команды в терминале, который публикует логи. Примеры выше показывают имена файлов; перейдите в каталог `migration-backups` перед запуском или укажите к нему полный путь.

Перед восстановлением ещё раз убедиться, что URL назначения относится к **НОВОМУ** проекту. Официальная команда восстановления (запускать только после проверки резервных копий и целевого project ref):

```powershell
psql --single-transaction --variable ON_ERROR_STOP=1 --file roles.sql --file schema.sql --command "SET session_replication_role = replica" --file data.sql --dbname "$env:LECTRIS_NEW_DB_URL"
```

При ошибке **остановиться и проверить журнал**. Не обходить ошибки удалениями схем/пользователей без анализа. В случае особых Vault/шифрования, изменённых managed schemas `auth`/`storage` или кастомных ролей следовать соответствующим разделам официальной инструкции. После окончания работы удалить из консоли секреты:

```powershell
Remove-Item Env:LECTRIS_OLD_DB_URL -ErrorAction SilentlyContinue
Remove-Item Env:LECTRIS_NEW_DB_URL -ErrorAction SilentlyContinue
```

ВНИМАНИЕ: команды для выгрузки и восстановления приведены для ориентира, **не выполнялись и не тестировались на реальном проекте**. На некоторых конфигурациях потребуются дополнительные действия из актуальной инструкции Supabase.

## Этап 3. Storage и конфигурация

- Зафиксировать перечень Storage buckets и количество файлов через `supabase/lectris_migration_audit.sql`.
- Скопировать **реальные файлы** между проектами посредством Storage API (официальный пример приведён в документации), затем сравнить количество и проверить реальные скачивания изображений/PDF. При использовании Beget S3 отдельно проверить его адрес, права и сохранность файлов.
- Воспроизвести **только** требуемые настройки новых API/Auth/SMTP/OAuth, Redirect URLs, email-шаблоны, Edge Functions, Storage buckets/policies и Realtime publications.
- Проверить поддерживаемые расширения БД, триггеры и RLS. Для логического restore проверить восстановление функций и правил в managed schemas.
- **JWT ключи и сессии:** по умолчанию старые браузерные токены могут не действовать. Войти заново с тем же email/паролем. Старый JWT secret НЕ надо переносить в публичный фронтенд.

## Этап 4. Новые таблицы Lectris

**Только после** успешного переноса исходной схемы на **новый** Supabase применить:

```text
supabase/lectris_organization_v1.sql
```

Этот файл создаёт безопасные таблицы предметов и групп с RLS. Его **никогда нельзя выполнять в старом Supabase**.

## Этап 5. Проверка перед переключением

В обоих проектах выполнить `supabase/lectris_migration_audit.sql`, сравнить результаты (с поправкой на новые таблицы Lectris). Проверить на **отдельном тестовом устройстве или адресе**:

- Вход нескольких существующих пользователей по прежнему email/паролю.
- Роли преподаватель/ученик/администратор, утверждение преподавателей и невидимость администратора.
- Количество досок, владелец и участники, права viewer/editor/owner.
- Открытие тяжёлой доски, рисунки, ластик, undo/redo, история и онлайн-синхронизация двух пользователей.
- Изображения, PDF, вложения, экспорт и импорт доски.
- Задания, уроки, расписание, сообщения, шаблоны, уведомления.
- Создание предмета/группы и отображение структуры с другого устройства.

Если хотя бы важная проверка провалена, **не менять старые настройки**. Исправлять исключительно новый проект.

## Этап 6. Переключение ТОЛЬКО Lectris

В `C:\Users\user\InteractiveBoardNext\.env` после успешной проверки указать **новые** URL и publishable/anon key:

```dotenv
VITE_SUPABASE_URL=https://NEW_PROJECT_REF.supabase.co
VITE_SUPABASE_ANON_KEY=NEW_PROJECT_PUBLISHABLE_KEY
VITE_LECTRIS_ISOLATED_SUPABASE_REF=NEW_PROJECT_REF
VITE_LECTRIS_ORG_SYNC=true
```

После этого перезапустить `npm run dev`. Никаких секретов `service_role`/secret API/database password в `VITE_*`, GitHub или `.env` приложения!

**Не менять** старый `OnlineRepetitor` `.env` и настройки старого Vercel. Не удалять старый Supabase. После перехода записи старого и нового проектов **не синхронизируются автоматически**. При затянувшемся переносе потребуется новая контрольная копия или согласованное окно без редактирования данных.

## Что ещё не сделано

- Отдельный Supabase **не создан** и доступ к проектам **не подключён**.
- Никаких реальных резервных копий или восстановления **не выполнялось**.
- Старые аккаунты пока находятся в исходной базе.
- Новые ключи и запуск Lectris на отдельной БД появятся только после действий владельца по созданию/подключению проекта и проверки.
