## 5. Права: обязательный контракт и уязвимые пути

Для ученика/гостя с разрешением editor:
- Создание нового задания, изменение условия, структуры или эталонного ответа: **нет**.
- Ответ, подпись, свободное письмо/рисование, изменение собственных учебных ответов: **да**.
- Перенос/масштаб незаблокированного объекта учителя: **да**, даже если это объект задания; структура/эталон остаются неизменны.
- Заблокированный преподавателем объект: **не перемещать и не изменять размер**, но **можно отвечать** на задание внутри.
- Удаление объекта другого пользователя: **нет**, даже если разрешено двигать.
- Удаление собственного незаблокированного объекта: **да**.
- Удаление собственного заблокированного объекта: **Требуется решение** только если текущая модель не определяет его однозначно. Не делать произвольный выбор без изучения UX.

Пути обхода и тесты: одиночное/групповое/рамочное выделение; выделение группы с чужими и своими объектами; Delete/Backspace, Ctrl+X, Ctrl+D, Alt-drag, копирование/вставка, undo/redo; меню «Ещё действия», контекстное меню, программные преобразования, загрузка импортированного JSON, reconnect и сравнение версий; две реальных отдельные JWT. Проверять сохранение creator/authorId после сериализации и повторного входа. Клиентский preview роли НЕ является серверной защитой.

ПРЯМОЙ АУДИТ MAIN: в src/boardModel.ts Item нет идентификатора автора; src/App.tsx deleteSelected фильтрует только lockedIds и protected student kinds и не сверяет пользователя. При mixed selection достаточно одного чужого незаблокированного объекта, чтобы его удалить. До разрешения миграции legacy объектов нельзя приписывать всем старым объектам автора по догадке. При внедрении авторства учитывать не только Item, но и штрихи из InkEntry; копия/группа/Undo не должны получать несанкционированное авторство.

В docs/BOARD_ROLE_AUDIT.md уже зафиксировано, что Supabase can_edit_board не валидирует поля JSON на сервере: editor-ученик теоретически может обойти браузерный запрет прямым API. **P0 блокирует публичный выпуск:** нужен доказанный server-side валидатор/ограничение прав на изменение структур задания и чужих объектов. Не внедрять непротестированный SQL на рабочую базу: сначала проект миграции + автоматические тесты политик с изолированными пользователями.
